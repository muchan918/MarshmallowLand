# 세이브 파일 암호화

> 이 문서는 `player.json`과 `run-save.json`의 암호화 파일 형식, 키 생성 방식,
> 기존 평문 파일 호환 및 암호화 형식 변경 규칙을 설명한다.
> 저장 대상과 데이터 버전 마이그레이션은 `Docs/Core/SaveSystem.md`를 함께 따른다.

## 1. 목적과 범위

싱글 플레이 환경에서 사용자가 세이브 파일을 직접 열어 플레이어 정보와 Run 진행 데이터를
쉽게 확인하거나 수정하는 일을 어렵게 하는 것이 목적이다. 완전한 키 은닉이나 경쟁 게임 수준의
치트 방지를 목표로 하지 않는다.

| 파일 | 저장 방식 | 이유 |
|---|---|---|
| `player.json` | 암호화 바이너리 | 슬롯 식별 정보와 튜토리얼 진행 상태 보호 |
| `run-save.json` | 암호화 바이너리 | 자원·웨이브·타워 등 현재 Run 진행 상태 보호 |
| `settings.json` | UTF-8 평문 JSON | 화면·사운드·언어 등 사용자가 수정해도 게임 진행에 직접 영향을 주지 않는 공통 설정 |

암호화 파일도 기존 경로와 파일명을 유지한다. 따라서 확장자는 `.json`이지만,
`player.json`과 `run-save.json`의 실제 내용은 사람이 바로 읽을 수 없는 바이너리다.

## 2. 관련 코드와 책임

| 코드 | 책임 |
|---|---|
| `Assets/Scripts/SaveData/Common/CryptoUtil.cs` | 키 생성, AES 암호화·복호화 |
| `Assets/Scripts/SaveData/Common/SaveFileStore.cs` | 파일 형식 판별, 암호화 적용, 평문 호환, 파일 읽기·쓰기 |
| `Assets/Scripts/SaveData/Common/SaveSerializer.cs` | JSON 직렬화·역직렬화와 데이터 버전 처리 |

`CryptoUtil`은 파일 경로나 JSON 구조를 알지 않는다. `SaveFileStore`는 JSON 내용을 해석하지 않고,
문자열과 파일 바이트 사이의 변환만 담당한다. 데이터 버전 확인과 마이그레이션은 기존 Serializer 계층이 담당한다.

## 3. 저장 흐름

```text
게임 상태
→ 저장 DTO 수집
→ JSON 직렬화
→ AES-256-CBC 암호화
→ NLSAVE01 + IV + 암호문 구성
→ .tmp 파일 기록
→ 기존 파일과 교체
```

1. 기존 저장 시스템이 게임 상태를 DTO로 수집하고 JSON 문자열로 직렬화한다.
2. `SaveFileStore.EncodeFile`이 암호화 사용 여부를 확인한다.
3. `CryptoUtil.Encrypt`가 JSON을 UTF-8 바이트로 바꾸고 AES-256-CBC / PKCS7로 암호화한다.
4. 암호화할 때마다 16바이트 랜덤 IV를 새로 생성한다.
5. `SaveFileStore`가 파일 형식 식별자 `NLSAVE01`을 암호화 결과 앞에 붙인다.
6. 완성된 바이트를 `.tmp`에 먼저 기록하고 성공 후 기존 파일과 교체한다.

같은 JSON과 같은 키를 사용해도 저장마다 IV가 달라지므로 서로 다른 암호문이 만들어진다.

## 4. 불러오기 흐름

```text
파일 바이트 읽기
→ NLSAVE01 확인
→ IV와 암호문 분리
→ AES-256-CBC 복호화
→ UTF-8 JSON 복원
→ 데이터 버전 확인·마이그레이션
→ DTO 역직렬화
→ 게임 상태 복원
```

1. `SaveFileStore.DecodeFile`이 파일 앞부분의 `NLSAVE01`을 확인한다.
2. 헤더를 제외한 데이터에서 앞 16바이트를 IV로, 나머지를 암호문으로 사용한다.
3. 저장할 때와 같은 AES 키와 파일에 들어 있던 IV로 JSON을 복호화한다.
4. 복원된 JSON은 기존 Serializer로 전달되어 데이터 버전 확인과 마이그레이션을 거친다.
5. 헤더가 없다면 기존 UTF-8 평문 JSON인지 검증한 뒤 기존 방식으로 읽는다.

암호화 파일의 복호화에 실패했을 때 해당 바이트를 평문으로 다시 해석하지 않는다.

## 5. 키 생성

실제 AES 키를 하나의 16진수 문자열로 보관하지 않고, 세 개의 고정 바이트 배열로 나누어 둔다.

```text
KeyPartA 16B + KeySalt 16B + KeyPartB 16B
                    ↓
             키 재료 48바이트
                    ↓ SHA-256
             AES 키 32바이트
```

- `BuildKey`가 세 배열을 정해진 순서로 연결한다.
- SHA-256이 48바이트 키 재료 전체를 AES-256에 필요한 32바이트 값으로 변환한다.
- 생성된 키는 실행 중 `CryptoUtil.Key`에 보관하며 저장과 불러오기에서 공통으로 사용한다.
- 키 재료의 값이나 연결 순서가 달라지면 다른 AES 키가 생성되어 기존 암호화 파일을 읽을 수 없다.

코드의 `KeySalt`는 사용자별 또는 저장별로 생성하는 암호학적 salt가 아니라 **고정된 키 재료의 한 조각**이다.
키 분할은 단일 키 문자열을 바로 검색하기 어렵게 하는 수준이며, 클라이언트 분석을 통한 키 추출을 막지는 못한다.

## 6. 암호화 파일 형식

```text
┌──────────────┬──────────────┬────────────────────┐
│ NLSAVE01 8B  │ 랜덤 IV 16B  │ AES 암호문          │
└──────────────┴──────────────┴────────────────────┘
```

| 영역 | 설명 |
|---|---|
| `NLSAVE01` | NorthLand 암호화 세이브 형식과 그 버전을 식별하는 ASCII 헤더 |
| IV | 해당 파일을 복호화할 때 사용하는 16바이트 초기화 벡터 |
| 암호문 | PKCS7 패딩 후 AES-256-CBC로 암호화한 UTF-8 JSON |

IV는 비밀 값이 아니며 복호화에 필요하므로 암호문과 함께 저장한다. AES 키는 파일에 저장하지 않는다.

`NLSAVE01`과 복호화된 JSON 내부의 `version`은 서로 다른 버전이다.

- `NLSAVE01`: 파일을 어떤 방식으로 해석하고 복호화할지 결정하는 암호화 형식 버전
- JSON `version`: 복원한 데이터 구조에 어떤 마이그레이션을 적용할지 결정하는 데이터 버전

## 7. 기존 평문 파일 호환

`NLSAVE01` 헤더가 없는 파일은 엄격한 UTF-8로 읽고, 앞의 BOM을 제외한 첫 유효 문자가 `{`인지 확인한다.
조건을 만족하면 기존 평문 JSON으로 취급한다.

```text
기존 평문 JSON 로드
→ 기존 Serializer로 검증·역직렬화
→ 게임 상태 복원
→ 다음 정상 저장부터 NLSAVE01 암호화 형식으로 기록
```

기존 파일을 읽는 것만으로 즉시 다시 쓰지는 않는다. 다음 정상 저장 시 암호화 형식으로 자연스럽게 전환한다.

## 8. 암호화 형식 변경 규칙

배포 후 키 재료, 암호화 알고리즘 또는 파일 바이트 구조를 변경하면 기존 `NLSAVE01` 파일을 그대로
복호화할 수 없을 수 있다. 이 경우 기존 헤더를 재사용하지 않는다.

1. 새 쓰기 형식에 `NLSAVE02`처럼 새로운 헤더를 부여한다.
2. 읽기 경로에는 `NLSAVE01`용 키와 복호화 코드를 보존한다.
3. 헤더를 기준으로 구버전 또는 현재 버전 복호화기를 선택한다.
4. 구버전 파일은 기존 방식으로 JSON까지 복원한다.
5. 다음 정상 저장에서는 최신 형식으로 기록한다.
6. 지원할 수 없는 헤더는 평문으로 재해석하지 않고 로드를 거부한다.

구버전 암호문을 직접 최신 형식으로 바꾸지 않는다. 반드시 구버전 방식으로 복호화해 JSON을 얻은 뒤,
최신 방식으로 다시 암호화한다.

현재 형식은 배포 전 개발 단계에서 확정한 `NLSAVE01`이다. 배포 전 테스트 파일은 삭제하고 다시 생성할 수 있지만,
배포 이후에는 사용자의 기존 세이브 호환성을 우선한다.

## 9. 검증 체크리스트

- [ ] 빈 문자열, 16바이트 경계 문자열, 한글 JSON을 암호화한 뒤 원문으로 복원할 수 있다.
- [ ] 같은 JSON을 두 번 암호화하면 랜덤 IV로 인해 서로 다른 바이트 배열이 생성된다.
- [ ] `player.json`과 `run-save.json`이 `NLSAVE01`로 시작하는 바이너리로 기록된다.
- [ ] `settings.json`은 UTF-8 평문 JSON으로 유지된다.
- [ ] 기존 평문 `player.json`과 `run-save.json`을 정상적으로 읽을 수 있다.
- [ ] 평문 파일을 불러온 뒤 다음 저장에서 암호화 형식으로 전환된다.
- [ ] 잘못된 헤더, 잘못된 암호문 길이, 잘못된 패딩을 정상 데이터로 처리하지 않는다.
- [ ] 실제 빌드에서 저장·재실행·이어하기가 정상 동작한다.
- [ ] 복원된 타워가 유지되며 선택과 전투 동작을 정상 수행한다.
- [ ] `.tmp` 기록 후 교체와 실패 시 기존 파일 유지 동작이 암호화 적용 후에도 유지된다.

## 10. 알려진 한계와 확장

- 키 재료와 복호화 코드가 클라이언트에 포함되므로 분석을 통한 키 추출까지 막을 수 없다.
- AES-CBC 암호화만으로는 파일이 의도적으로 변조되지 않았다는 무결성을 보장하지 않는다.
- 현재 목표는 싱글 플레이 세이브의 직접 열람과 단순 수정을 어렵게 하는 것이다.
- 무결성 검증이 필요해지면 새 암호화 형식 버전에서 AES-GCM 또는 CBC + HMAC 적용을 검토한다.
- 경쟁 요소가 있는 멀티플레이 게임에서는 중요한 상태를 서버가 소유하고 검증해야 한다.
